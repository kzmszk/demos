# 移動モジュール共通化提案へのレビュー

対象：`movement-unification-proposal.md`（2026-10-29）。提案と作業ツリーのコードを照合した設計レビュー。実装・依存インストール・ビルド・実機操作は行っていない。以下の行番号は現行ソースを指す。外部仕様を根拠にした保証ではなく、コードから確認できる事実と設計上の懸念を分けて記す。

## 1. 全体評価

**方向性には賛成。ただし、現状の公開インターフェースと検証計画のまま実装に入るのは勧めない。**

- `shared/move/` を相対 import し、three の直接依存を避ける骨子は妥当。4都市のビルドは bundle を作っており、移動計算のために依存管理まで統一する必然性はない。特に venice/kyoto の入力、指数補間、歩行の揺れには明確な重複がある。
- 地面データと衝突を都市側に残す判断はよい。alhambra の `Navigation.move` は細分移動と幾何判定を行い（`alhambra/tools/web/navigation.js:57-69`）、ラスター歩行の単なる設定違いではない。ツアーと共有されるこの境界を保つべきである。
- 操作感の変更を抽出から分離し、生成済み bundle も更新する方針に賛成する。ただし「互換プロパティがあれば呼び出し側はそのまま」という見積もりは楽観的。値の名前だけでなく、入力処理の時機、状態の所有者、更新順序まで互換にする必要がある。

## 2. 疑問・反論

### 2.1 インターフェース：設定が足りず、設定同士にも矛盾がある

**`smooth:0` は、記載された式では停止を意味する。** 提案の `1-exp(-smooth*dt)` に 0 を入れると補間係数は 0 になり、alhambra の fly は静止した速度から動けない。現在は毎フレーム直接変位を加算している（`alhambra/tools/web/main.js:179-182`）。`smoothing:null` を「即時代入」と定義するなど、無効化の意味を明文化すべき。

**入力合成と正規化は都市ごとに違う。** alhambra はキーボード＋スティックを合算した後、水平2成分をまとめて長さ1に制限し、上下は別に足す（同 `:177-182`）。提案の各成分を先に -1..1 に丸める処理とは一致しない。たとえば水平入力 `(forward,right)=(2,1)` は現行では比率2:1、成分ごとの clamp 後では1:1になる。一方、venice/kyoto は歩行だけ水平正規化し、飛行は斜め速度を制限しない（各 `controls.js:92-96,108-112` / `:97-101,135-139`）。共通 fly が一律に正規化すると既存の飛行速度も変わる。入力の合成・成分制限・水平正規化・上下合成の順序を契約に含める必要がある。

**座標の入れ替えだけでは yaw の意味は揃わない。** z-up の yaw=0 は +x、右方向は -y（`venice/tools/web/controls.js:86`）。alhambra の yaw=0 は -z、右方向は +x（`main.js:181`）。`up:'y'` に何を含めるか、前方・右方・正の旋回・pitch の基準を定義し、四方位で往復変換を検証したい。既存の `drawMap` は Euler の yaw を直接読む（同 `:110`）ので、内部で yaw の基準を統一するなら互換変換も必要になる。

**three 非依存のカメラ契約が未完成。** 現在の `syncFromCamera()` は THREE.Vector3 を `getWorldDirection` に渡す（3都市の同名メソッド）。提案の自前 Vec3 に列挙された `set/lengthSq/lerp` だけで、その出力引数としても使えるとは確認できていない。都市側の `readDirection()` / `applyLook()` を注入すれば、three の内部的なベクトル要求を共通コードに持ち込まずに済む。`opts.Vector3` を残す案とカメラアダプター案は、責任境界が異なるので先に選ぶべき。

**状態の所有者とモード別入力が不明。**

- `speed` は Mover の可変プロパティと `flyMode({speed})` の両方にある。ホイールがどちらを書き換えるのかを定める必要がある。`yaw/pitch` と `ctx.look`、`camera.position` と `ctx.pos`、ワールド座標の `vel` と正規化座標の速度も同様。
- boat は単に最後の `look.apply()` を飛ばせばよいわけではない。ドラッグは `boatYaw/boatPitch` を変更し、通常の yaw/pitch には触れない（`venice/tools/web/controls.js:21`）。`boatMode.update(ctx,axes,dt)` にドラッグ差分が渡らず、この状態も公開契約にない。モード別の look 処理か、生の look 入力を受ける口が必要。
- 歩行ラスターの未ロード時には既存 update は look の適用前に return する（venice `:87-91`、kyoto `:92-96`）。「false は boat 用」という説明を一般化し、位置・視点を適用しない結果を明示したい。
- kyoto の walk 入場時 pitch 上限は 0.6（`controls.js:35-37`）。提案の既定 0.5 に対して、都市別設定例に上書きがない。小さな違いでも互換を主張するなら埋めるべき。

### 2.2 ラスター歩行：`slide` だけの差ではない

kyoto の `cost/can` は端の点が塞がっていても、塞がった方向へ進まなければ許す（`kyoto/tools/web/controls.js:59-77`）。venice は5点すべての通行可能性を要求する（`venice/tools/web/controls.js:58-64`）。また、kyoto は現在地点の中心が不通なら `through` で blocked を無視し（`:103-104`）、動けない場合は速度を半減する（`:126-129`）。venice は停止時にゼロにする（`:100-102`）。したがって kyoto を移して `slide:'axis'` にするだけでは再現できない。移動候補生成と通行判定・脱出規則・衝突後速度を分けるか、最初は2つの歩行戦略として残したい。

特に venice の blocked 高さを0に置換するアダプターについて、「z は判定で使わないのでダミーでよい」という断言には条件が要る。blocked を常に拒否する専用戦略なら成立するが、kyoto の `through` が有効になるとダミー高さが通行可否や高さ追従に混入し得る。水面・建物・未ロードの3状態を保持し、venice には blocked 脱出を適用しないことを契約にするべき。

### 2.3 `shared/` と esbuild：採用できるが、完了条件を補いたい

相対パスの段数は正しい。4つの `build_web.mjs` が `bundle:true` を指定しており、共通コードをブラウザーから別途取得しない構成は自然。ただし「ビルド設定の変更不要」は、共通ファイルの解決に限った説明に狭めたい。

- venice/kyoto/vatican は相対 entry/output を使い、alhambra だけ `absWorkingDir:here` を指定する（各 `build_web.mjs:4`、vatican `:5`、alhambra `:12`）。全都市再ビルドの実行ディレクトリを固定しないと、ルートからの単純な一括実行は成立しない。
- vatican の絶対パス解消と tools への esbuild 追加は賛成。ただし alhambra の resolver は vatican をフォールバック先にする（`alhambra/tools/build_web.mjs:7-9`）。そのままコピーすると vatican 自身をフォールバック先にするため、ローカル依存を素直に解決する形でよい。依存追加に伴う vatican の lockfile 更新も完了条件に入れる。
- ビルドツールの解決を変えた直後に bundle のバイト差分ゼロを要求するのは強すぎる。従来の絶対パス先の esbuild バージョンが不明なら、生成差分だけで移動の回帰とは判断できない。バージョンを記録・固定し、ツール変更と挙動比較を分ける。
- shared 変更時の全利用都市ビルドを、注意書きだけにしない。利用都市一覧と一括チェック用の入口を用意する。生成物による「暗黙のピン留め」は、同時にソースと公開物が食い違うリスクでもある。

今回 gallery/ルートの未展開ファイルは取得できず、`git status` も不足オブジェクトの取得に失敗した。デプロイが既存 bundle をコピーするだけなのか、都市を再ビルドするのかは未確認として残す。shared を配信する必要と、ビルド環境に含める必要は分けて確認したい。

### 2.4 移行順序：条件付きで妥当。ただし準備段階が大きすぎる

vatican をビルドと飛行の試験台にし、alhambra を最後にする順序は合理的。kyoto→venice は高機能側を先に検証できる利点がある。一方、§4.0 で kyoto 全体を一般化してから vatican に入ると、最初の利用者が検証しないラスター抽象化を大量に先行実装することになる。

順序自体を変えるより、**vatican の段階では入力・視点・飛行だけを抽出し、ラスターは kyoto の段階で初めて導入する**方がよい。その後 venice で第2の歩行戦略としての差分を検証する。2都市目で共通APIを見直す余地を明記してほしい。alhambra は入力・視点だけの共通化に留める選択肢も残す。

### 2.5 検証計画：現状のゴールデントレース手順はそのまま動かない

- `VAT` は `controls` を公開していない（`vatican/tools/web/main.js:273-280`）。したがって提案の `controls.keys` 注入・yaw/pitch 記録にはアクセス経路がない。さらに `VAT.stopLoop()` は controls を無効化する（`:275`）。`VAT.look()` は再び free にして有効化するが、呼び出し順を規定しないと静止トレースを比較するだけになる。
- vatican の RAF は `looping` を確認して次回を予約する方式（`:254-259`）。stopLoop は予約済みフレームをキャンセルしないため、停止後のフレームが消化されたことも確認したい。
- 固定 dt だけではストリーミングの再現性は得られない。VEN/KYO の step は controls の後に `tiles.update` を呼ぶ（venice `:358-359`、kyoto `:409-410`）。未ロードの期間や取得完了順によって、歩行開始と探索結果が変わる。固定サンプラーによるロジック比較と、必要タイルのロード完了を待つ実シーン比較を分けるべき。
- `ALH.move` と既存経路検査は Navigation の安全性を検証できるが、今回置き換えるキー・スティック合成、飛行、ドラッグ、orbit との切替は検証しない。ここにも実入力を通す比較が必要。
- 位置だけでなく向き、速度、walkZ、モード遷移を比較したい。yaw は2πの折り返しを考慮し、向きは方向ベクトルでも比較する。1e-6 m は固定データ・固定演算順の試験には候補になるが、非同期実シーンの一律合格基準にはできない。

### 2.6 見落としやすい入力・外部カメラとの結合

alhambra は `pauseInput` でキーだけでなく stick・alt・pointer を消し（`main.js:114`）、blur/visibilitychange でも入力を消す（`:136-137`）。`ignore(e)` は新しいイベントを無視するだけで、既に保持した入力を解除しない。`resetInput()` と、ダイアログ・非表示・外部カメラ制御への遷移で呼ぶ規則が必要。

また、orbit 中 `mover.enabled=false` にするだけでは、都市側と共通側でポインターやホイールを二重処理し得る。現行は同じ pointermove 内で orbit と通常視点を分岐している（`:128-130`）。入力の所有権をモードごとに一つにし、無効化が「積分停止」なのか「入力受付停止」なのかを明記すべき。orbit のスティック操作は walk へ遷移する（`:140`）ため、全面的な入力無効化もそのままでは適用できない。

ツアー停止通知も `key|drag|stick` だけでは不足する。alhambra は pointerdown、orbit ホイール、rise/descend の押下でも止める（`:127,130,142`）。一方 vatican は操作すれば自動的にツアーを止める実装ではなく、F やUIで free に入る。両者を同じコールバック設定にして挙動を追加しないようにしたい。

## 3. 追加・代替案

最初から全体を統括する Mover を完成させるより、次の小さな境界で始めることを勧める。

1. 入力状態の集約と解除、座標変換を含む視点アダプター、飛行の速度・変位計算を独立させる。共通計算はDOMやカメラを所有しない。
2. 当初は既存 Controls を互換ファサードとして残し、`keys/speed/vel/walkZ` とモード遷移の既存契約を維持する。自前の万能Vec3を育てる前に、都市側の THREE.Vector3 を残す案も比較する。
3. ラスターは venice の厳格な5点判定と kyoto の脱出・滑走判定を別戦略にし、サンプリング、探索、補間、揺れなど確認できた重複を共有する。差分を一つの `slide` 設定に押し込まない。
4. 旧実装と抽出後の実装へ同じ初期状態・入力列・固定サンプルを渡す比較試験を先に成立させる。その後、ブラウザーでイベント受付・遷移・外部撮影フックを確認する。

この構成なら vatican→kyoto→venice→alhambra を維持しつつ、共通化の利益と抽象化の負担を各段階で判断できる。全都市が同じ Mover を使うこと自体は完了条件にしない方がよい。

## 4. 末尾の2つの判断事項への意見

**フレームレート依存の旋回は直す。ただし抽出の互換確認後、別変更で行う。** venice 0.02、kyoto 0.025 rad/frame（各 `controls.js:44-45` / `:43-44`）は、60Hz基準なら1.2 / 1.5 rad/sに相当する。移行時点では既存値を保存し、次の変更で dt 比例にする。30/60/120Hzで同じ実時間の旋回角を比較し、アプリ側 dt の上限処理も含めて確認する。指数補間＋離散積分の軌跡全体まで完全一致を要求する必要はない。`perFrame` は恒久APIというより移行用の互換設定と位置づけたい。

**alhambra のドラッグ方向は今回揃えない。** 現行は意図した操作としてコメントされ（`main.js:128`）、orbit の theta/phi 操作も別に定義されている。まず同じポインター変位に対するワールドの視線変化を検証し、Euler の符号比較だけで結論を出さない。そのうえで共通の操作方針を採るなら、orbit・walk・flyを往復した体感とマウス／タッチ双方を確認する独立したUI変更にする。共通化の利益を得るために方向まで合わせる必要はない。

## 5. ブラッシュアップで必ず直すべき点トップ3

1. **挙動保存に必要なAPI契約を具体化する。** `smooth:0`、入力の合成と正規化順序、座標・yawの基準、speed/velの所有者、boatのlook入力、未ロード時のreturnを定義する。kyoto の pitch 上限0.6も設定例へ反映する。
2. **venice を kyoto の `slide:'axis'` だけで再現できるという前提を撤回する。** 通行判定・blocked脱出・衝突後速度を分け、blockedのダミー高さが安全な条件も明記する。
3. **実行可能な検証手順へ書き直す。** VATの入力アクセス・stopLoop副作用、ロード完了条件、alhambraの入力経路の検査不足を解決する。vaticanでは飛行まで、kyotoでラスター導入という段階にし、全利用都市のビルド手順と依存固定も完了条件へ入れる。
